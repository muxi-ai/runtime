**MUXI's SOPs are fundamentally different**. They're not sequences to be followed blindly, but rather:
- **Institutionalized knowledge** that agents can reason over
- **Reusable "how-to" scaffolds** that adapt to context
- **A shared semantic memory layer** for procedural wisdom

When MUXI encounters an incident, it doesn't robotically execute steps 1-2-3. Instead, it:
1. **Recognizes** the situation matches an incident pattern
2. **Retrieves** relevant procedural knowledge from SOPs
3. **Reasons** about which aspects apply to this specific context
4. **Adapts** the guidance based on real-time conditions
5. **Decides** autonomously how to proceed

This is the difference between a puppet following strings and an intelligent system leveraging organizational wisdom. SOPs become part of the agent's knowledge graph – consulted, not commanded.

## Technical Architecture

MUXI is composed of four major layers, mirroring the Docker ecosystem:

### 1. **MUXI Runtime**: Formation runtime framework

> Analogy: Docker Container

* Licensed under Elastic 2.0
* **Contains all Core Intelligence Capabilities**: Autonomous intelligence, Overlord orchestration, A2A protocol, proactive task scheduling, smart memory management, document intelligence, MCP tool integration, LLM model resilience, async request-response system, and extensible architecture
* **Contains all Enterprise Infrastructure Features**: Production resilience, enterprise-grade security, built-in observability, built-in file generation from code, multi-LLM support, infrastructure-as-code, session isolation, traceable chain-of-thought, scheduled task management, and complete DevTools
* **Runs individual formations** as self-contained AI systems with all capabilities included
* **Self-hostable, Docker-deployable** runtime instances that execute the actual AI agents and their workflows
* **Embeddable Framework**: Can be integrated directly into existing applications as a library, enabling developers to add MUXI's AI capabilities to their current tech stack without requiring separate infrastructure deployment

### 2. **MUXI Server**: Formation orchestration engine

> Analogy: Docker Daemon

* Licensed under Elastic 2.0
* **Orchestrates multiple MUXI Runtime instances** (multiple formations running simultaneously)
* **Provides comprehensive API security layers** for external access, authentication, and authorization
* **Manages formation lifecycle** - start, stop, restart, scale, and monitor multiple formation runtimes
* **Handles coordination between different runtime instances** and cross-formation communication
* **Enterprise management features** - user management, resource allocation, billing, monitoring dashboards
* **Production deployment infrastructure** - load balancing, auto-scaling, health checks, and operational management

### 3. **MUXI Formation**: Declarative AI system blueprints

> Analogy: Dockerfile

* Licensed under Apache 2.0
* Formation-based YAML configurations that package complete AI systems as portable, reproducible units
* Version-controlled system definitions with agents, memory, tools, scheduling, security, and orchestration specifications
* Multi-agent coordination: Task delegation and coordination are handled via a built-in Overlord engine.

### 4. **DevTools**: Developer ecosystem

* Licensed under Apache 2.0
* **CLI**: Command-line interface for formation management and deployment
* **SDKs**: Python, JavaScript, Go, and other language bindings
* **Studio**: Web-based UI for formation development, testing, and monitoring

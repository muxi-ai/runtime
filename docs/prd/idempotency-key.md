# Idempotency Key Support

**Date:** 2026-01-05
**Status:** Deferred (placeholder in API spec, not implemented)
**Priority:** Low

---

## Overview

`idempotency_key` is a client-provided identifier to ensure duplicate requests are not processed twice. Currently exists as a placeholder in the API response schema but is not functional.

## request_id vs idempotency_key

| | `request_id` | `idempotency_key` |
|---|---|---|
| **Generated by** | Server | Client |
| **Purpose** | Trace/observe request | Prevent duplicate processing |
| **Use case** | "Show me logs for request X" | "If I retry, don't run twice" |
| **Current status** | Implemented | Placeholder only |

## How It Would Work

```
┌─────────────────────────────────────────────────────┐
│ Request with idempotency_key                        │
└─────────────────┬───────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────┐
│ Check DB: SELECT * FROM idempotency_cache           │
│           WHERE key = ? AND expires_at > now()      │
└─────────────────┬───────────────────────────────────┘
                  ▼
         ┌───────────────────┐
         │  Key exists?      │
         └───────┬───────────┘
           Yes   │   No
            ▼    │    ▼
   Return cached │  Process request
   response      │  Store result in cache
                 │  Return response
```

**Example scenario:**
```
1. Client sends: {message: "create report", idempotency_key: "abc123"}
2. Server processes, network dies before response reaches client
3. Client retries: {message: "create report", idempotency_key: "abc123"}
4. Server: "Already processed abc123" → returns cached result (no duplicate)
```

| Middleware | 2 hours | Check cache before processing, store after |
| Race condition handling | 1 hour | Lock when same key arrives while processing |
| TTL cleanup | 30 min | Cron job or lazy delete expired entries |
| Tests | 1-2 hours | Unit + integration tests |
| **Total** | **4-6 hours** | |

## Value Assessment by Endpoint

| Endpoint | Value | Rationale |
|----------|-------|-----------|
| Chat (sync) | Low | Duplicate messages aren't harmful |
| Chat (async) | Medium | Prevents duplicate background tasks |
| Create scheduled job | **High** | Don't want duplicate jobs created |
| Register trigger | Medium | Could fire same trigger twice |
| Admin operations | Low | Typically done manually, not automated |

## Decision

**Deferred.** Remove from API spec or keep as placeholder.

**Rationale:**
1. Low value for primary use case (chat)
2. `request_id` already handles "check status of pending request"
3. Premature abstraction - no customer demand yet
4. Can add later when enterprise customers need it for scheduled jobs

## When to Revisit

Implement when:
- Enterprise customers request it for scheduled job creation
- We add billing/metered operations where duplicates cost money
- Webhook delivery needs exactly-once semantics

## Current State

- Response schema includes `idempotency_key` field (always `None`)
- No endpoint accepts `idempotency_key` as input
- No caching/deduplication logic exists
